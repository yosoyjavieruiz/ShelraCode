## Ground truth about the current codebase (verified by direct code inspection today, not guessed)

Use this to keep the research and the resulting Master Prompt **specific to this codebase**, not generic agent-architecture advice:

- **Core loop is a monolith.** `src/agent/loop.ts` is a ~5,500-line `runAgent()` function concentrating turn/tool-call handling, four separate "non-progress watchdogs," model-plan lifecycle, verification gating, and recovery/replan logic in one file. `src/tui/app.tsx` similarly concentrates UI + task-lifecycle wiring. This is the single biggest architectural liability the prior research flagged, and it is still true today.
- **No real per-model quality calibration exists.** Until today, every discovered model candidate (local via LM Studio/Ollama, and free-cloud via Groq/OpenRouter) received a **flat, hardcoded `quality.coding`/`quality.toolUse` score** (`0.6` for all local models regardless of parameter count; `undefined` → defaulted to `0.5` for all free-cloud models) inside `src/runtimes/http.ts`, `src/runtimes/ollama.ts`, and `src/providers/openai-compatible.ts`. The router (`src/router/router.ts`) scores candidates on `taskFit` (weight 0.3, the highest) using exactly that field, plus a `quotaOpportunityCost` that further penalizes cloud routes for "low-value" tasks and zero-penalizes local — meaning the router was structurally biased toward whichever local model was loaded, regardless of whether a much stronger free-cloud model (e.g. Groq's `gpt-oss-120b`) was available for free. I patched this today with a crude heuristic (`src/shared/model-quality.ts`: score derived from parsed parameter count + a "coder" keyword bonus in the model name) — this is a stopgap, **not** the empirical, protocol-aware "Shelra Driver" calibration the prior research calls for.
- **Repository intelligence is Level 1 only** (path/Git/manifest/lexical `rg`-style search). No AST symbol table, no imports/exports graph, no definitions/references/implementations, no LSP integration, no related-test discovery. This matches the prior audit's "3/10" score and is unchanged.
- **The planner (`src/agent/planner.ts`, `src/agent/task-contract.ts`, `src/agent/objective-review.ts`) is host-validated but keyword/regex-heavy.** It compiles a `TaskContract` (deliverables, acceptance criteria, evidence requirements) from the user's natural-language request using regex-based intent detection (e.g. `describesMutation()`, `isGreenfieldObjective()`), accepts an LLM-authored append-only task graph (`ProposeTaskPlan` tool), and recovers via `appendModelRecoveryPlan()` which requests a new plan revision from the model when the current one is stuck (bounded to ~2 attempts). `objective-review.ts` does clever but ad hoc host-side cross-artifact checks (e.g., parses HTML for `<script src>` and JS for `querySelector`/`getElementById` calls and flags selector mismatches) — useful evidence but not a general capability.
- **Today I fixed one concrete, evidenced defect class**: three of the four "non-progress watchdogs" in `loop.ts` (repeated identical tool call, repeated tool error, repeated failed mutation) used to hard-abort the entire task on first trip; only the fourth (mutation stagnation) attempted `appendModelRecoveryPlan()` first. I unified all four through the same recovery path, verified with a real (non-mocked) integration test and a real end-to-end run against a locally loaded Qwen2.5-Coder-7B-Instruct model via LM Studio (`scripts/evaluate-agent.ts --local-only`), which completed a real read→edit→`bun test`→verify cycle successfully.
- **Subagent scaffolding exists but is unused in the main coding flow**: `src/agent/subagents/coordinator.ts` (`ForegroundSubagentCoordinator`), `src/agent/code-review-agent.ts` (a read-only, ledger-based "code review" that never edits files and never trusts model prose). Neither is currently gated behind any A/B proof of improvement — they are wired in but not measured.
- **An existing, already-approved architecture doc is in-repo**: `docs/superpowers/specs/2026-08-26-level-10-agent-architecture.md`, a 7-phase plan (1. objective contract & truthful completion, 2. repository intelligence, 3. durable task runtime, 4. process/network/workspace safety, 5. skills & instruction hierarchy, 6. isolated delegation, 7. product evidence & release closure) with explicit non-goals and a "level-10 readiness" definition gated on fresh evidence, not self-assessment. This predates the Self-Calibrating Runtime thesis and has NOT been reconciled with it. **Your Master Prompt must explicitly diff against this existing plan**: state what to keep as-is, what to refactor, and what to discard, rather than proposing a parallel roadmap that ignores work already scoped/in-progress.
- **Test suite is ~740 tests, ~97% passing, but historically dominated by deterministic fixtures and fake providers rather than demonstrated real-model task completion** — exactly the failure mode the prior audit scored 4.2/10 on. Today was the first time a real local model was driven through the real `runAgent()` loop end-to-end as part of this work (not as a one-off manual check).
- **Product/routing facts**: strict-zero routing never selects a paid route; verified-free cloud (Groq, OpenRouter) and local runtimes (LM Studio, Ollama) are both eligible. Windows is the primary dev platform (PowerShell + Bash tool duality matters for any shell-execution design). Bun is the runtime/test-runner; TypeScript throughout; no framework beyond OpenTUI/SolidJS for the TUI.
