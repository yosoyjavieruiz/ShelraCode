## Synthesis

The common architecture is a strong harness around a capable model: explicit
policy, bounded tools, a real model-tool-result loop, evidence tracking,
verification, recovery, and a completion decision owned by the application.
The sources do not justify a giant system prompt, automatic provider
escalation, or capability claims based only on a model name.

The most immediate LocalCode consequences are:

1. Fix deterministic turn classification and structural tool policy before
   tuning prompts.
2. Separate model text, structured tool calls, tool observations, and UI
   activity; never render tool arguments as assistant prose.
3. Replace the boolean `verified` default with evidence and completion gates.
4. Probe the exact model/runtime/template/parser combination and persist the
   result before routing a coding task.
5. Treat compaction, cancellation, permissions, and traceability as kernel
   correctness, not visual features.

### Current local model recommendation evidence

The official [Qwen2.5-Coder-7B-Instruct-GGUF model card](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct-GGUF)
was checked on 2026-08-24. It identifies the model as a 7.61B-parameter causal
code model, lists GGUF Q4_K_M/Q5_K_M variants, and documents 32,768-token GGUF
context. The card lists Q4_K_M at approximately 4.68 GB and explicitly names
LM Studio among supported local applications. Consequence: for the current
15.2 GB machine, Q4_K_M is the first stronger local candidate to measure; this
is a fit recommendation, not an autonomous-coding capability claim.

### LM Studio native model metadata checked in the implementation pass

The official [LM Studio model-list REST documentation](https://lmstudio.ai/docs/developer/rest/list)
and [REST API overview](https://lmstudio.ai/docs/developer/rest) were checked
on 2026-08-24. The native `/api/v1/models` response distinguishes model type,
key, display name, quantization, size, context, architecture, and capability
metadata. Implementation consequence: use native metadata as optional runtime
enrichment, retain the provider key separately from the user-facing name, and
fall back to the OpenAI-compatible `/v1/models` endpoint when native metadata
is unavailable. Native metadata must never replace empirical capability
probes or the router's coding eligibility gate.

### Live LM Studio/Qwen follow-up checked 2026-08-24

The current official [LM Studio tool-use documentation](https://lmstudio.ai/docs/developer/openai-compat/tools)
states that tool parsing depends on the model/template, that smaller or
non-tool-trained models may emit malformed calls, and that LM Studio may leave
those calls in assistant `content` instead of `message.tool_calls`. It also
distinguishes native tool-use support from default compatibility behavior.

Implementation consequence: the 7B result is recorded as a concrete
model/runtime/template observation, not generalized from its name or parameter
count. LocalCode may recover a bounded textual envelope through its normal
schema boundary, but it must continue to require empirical edit, test, and
verification evidence before routing coding work. The direct live observation
matches the documented failure mode: empty native `tool_calls` with
tool-shaped assistant text.

The same official LM Studio page lists
`lmstudio-community/Qwen2.5-7B-Instruct-GGUF` as a current native-tool-use
model and marks native support with the hammer badge. Consequence for the
next live comparison: prefer that exact native-tool-use variant, or another
model with the hammer badge, over downloading a larger model whose
template/parser combination is unverified. Native support is only an
eligibility signal; LocalCode must still run its complete capability probe and
disposable coding acceptance.
